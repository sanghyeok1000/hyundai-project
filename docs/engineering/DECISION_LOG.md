# BEYOND PHYSICS 설계 결정 기록

## 2026-11-05 출품 준비와 세 맵 감각 효과

사용자는 새 맵 추가보다 세 맵을 다듬고 계획서·영상·GitHub 프로젝트/APK·제출 준비를 진행하기로 했다. 우선 조명·공조·사운드를 맵 의미에 맞춰 실제로 연결한다. C++ 물리 상태에서 독립 효과 정책을 계산하고 Unreal 오디오와 기존 Kotlin/JNI SDK 출력으로 나눈다. 차량의 입력/물리 모델·도로·μ는 유지한다. 효과 개수별 가산점은 확인되지 않았으며 공식 기준의 적절한 기술 활용성과 개발 산출물 가산점을 구분한다.

조명/공조는 초기OFF, 소리는ON이다. 공조 전원/AUTO/AC를 강제로 바꾸지 않고 켜진 수동 공조의 약한 팬과 선택적1°C 냉감만 사용한다. 맵03은 온도를 유지한다. 원본 캡처·쓰기 의도 journal·실제getter 확인·사용자 변경 양보·지연 요청/heartbeat·원상복원을 별도 소유권 모델로 구현했다. GameActivity foreground와 Android 오디오 포커스는 서로 달라 별도로 등록/초기 허용/손실을 처리한다.

실측 차이: Vehicle2.3.2 Light.kt 공개 권한과 LightImpl.kt 내부 제어 권한이 달라 CONTROL_CAR_LIGHTS도 선언했다. 팬/온도/전원 영역이 다르므로 각 API의 실제 광고 영역을 골라 모든 영향 좌석의 전원/AUTO/AC guard를 확인한다. 선택적 ambient-auto capability가 명시적으로 ERROR_NOT_SUPPORTED_PROPERTY를 반환하면 그 보조 기능만 생략하고 나머지 오류는 숨기지 않는다. 에뮬레이터가 조명getter에RGB24(흰색16777215,청록3382463)를 반환하고 요청은ARGB32인 차이를 실제SDK로그로 확인해 emulator-only 불투명색 호환 처리를 추가했다.

## 2026-11-04 안개 피드백과 일반 승용차 선택

사용자는 특정 차종 대신 근거를 기록한 일반 승용차 모델로 조향을 개선하도록 선택했다.18:1 랙비/2.7m 휠베이스/1.88m 윤거는 측정 차종의 값이 아닌 공개한 가정이다. 기존 bicycle 모델을 남기고 안개 맵만 네 접지점으로 확장하여 영윤거·정상선회·제동 분석해와 비교한다. 입력→Ackermann→현재 접지점 속도→각 타이어 힘→강체 힘/모멘트 합산→적분→같은 각도로 렌더링하는 경로다. 고속에서도 무조건 기하학 원을 따르도록 강제하지 않는다.

사용자 요청으로 안개 맵만 정지 출발 정책을80km/h 초기조건으로 바꾸고100까지 자동 구동한다. 접근을x=-260m로 줄이고30m 후 안개에 진입한다. 차로별 한 대를45/40m 간격으로 배치하고 공간 안개 밀도를0.27로 높였다.30m는 선언된 분석 기준이며 사람의 실제 발견거리 보정값이 아니다. 난이도는 짧은 시야·배치·계산된 접지력에서 만들며 마찰/요/속도를 몰래 보정하지 않는다. 기준 이전의 예방 제동도 유효한 정지 결과로 인정한다.

검토에서 첫 기준 차량과 뒤의 실제 접촉 차량이 다르면 간격 대상이 섞이는 문제를 확인했다. 기준 차량 간격을 끝까지 유지하고 접촉 차량 번호를 별도 저장하며 회귀 검사의 실패→수정 후 통과를 기록했다. 기존 두 얼음 맵 자산 해시는 작업 시작 백업과 동일하다.

## 2026-10-29 Unreal/Pleos 호환성과 제출 기준 재확인

사용자가 Unreal 결과물을 Pleos와 연결해 출품할 수 있는지 정확한 확인을 요청했다. 기술적으로는 Android APK의 Java/Kotlin SDK와 C++/JNI 연결 경로가 있으나 현재 프로젝트의 구동 성공은 미검증이다. 공개 공모전 규정은 Unreal 명시 허용/금지를 제시하지 않아 운영사 확인 전 공식 허용이라고 주장하지 않는다.1차 기획/영상 접수와2차 실제 앱 시연·최종 전시 APK 제출을 구분한다. 또한 Epic5.4 런처x86_64 바이너리/5.8 에뮬레이터 문서를 확인하여 'GitHub 소스 빌드 필수' 단정을 정정한다. 문서 일부가 상충하므로 현재 설치 구성과 최소APK로 실증한다. 개발용 PC 중계만으로 최종 APK 구동을 검증했다고 보지 않는다.

## 2026-10-29 자동 가속·브레이크 중심 체험

사용자는 실제 가속페달 사용을 제외하고 시작부터 자동 가속, 브레이크로 제동하는 방식으로 변경했다. PC는 S 제동/A-D 조향, W 입력 제거. 브레이크>0이면 구동 요청0, 해제 시 구동 요청1로 복귀하는 정책을 별도 순수 C++ 함수로 구현한다. 차량 운동 방정식이나 속도를 보정하지 않는다. 기존 B/T 실험·입력 재생은 별도 유지한다. 이 결정은 실차 브레이크·핸들 사용 안전 승인을 대신하지 않는다.

그래픽은 기존2km 도로에 가로등68개를 추가하고, 이전 산을 숨겨 보존한 뒤20만 삼각형의 능선 지형과 CC0 실사 PBR 암석을 적용한다. PC 품질을 확인하되 차량 APK 성능·자원 사용량은 검증 전으로 남긴다. 기준 지침은 PROJECT_GUIDELINES.md(v1.1)다.

## 2026-10-29 가속 증가와2km 도로

속도·도로 길이 증가 요청에 따라 기본 저마찰 μ를0.12→0.18로 조정했다. 기존 가상 AWD는 이미 μg에 포화되어 엔진 구동 요청 증가만으로 가속이 늘지 않는다. 시간배속·속도곱셈 대신 환경 파라미터를 명시적으로 바꾼다. 직선 전가속1.5배가 되며 제동·선회 접지력도 함께 증가한다. 일반 μ0.85, 정지 출발, 차량 질량·힘 모델·고정 적분은 유지한다. 도로/벽/표지2km, 출발점-440m/끝 제한±995m로 실제 전방 주행 거리도 약2배가 되게 맞춘다. 이전μ0.12도 회귀 검사에 남긴다. 복구 사본은 backups/longer-faster-road-20261029다.

## 2026-10-28 저마찰 주행의 계산 계층 선택

사용자는 별도 C++ 차량 모델로 운동을 계산하고 Unreal이 화면을 그리는 방식을 선택했다. 대안은 Unreal 기본 차량/Chaos를 먼저 활용해 주행 구현을 빠르게 시작하는 방식이었다. 선택 이유는 물리 방정식·가정·단위·오차를 직접 설명하고 검증하는 프로젝트 목표다. 엔진 제공 차량 메시·재질을 외형으로 활용하는 것은 가능하며, 외형 자산과 차량 운동 모델의 채택을 구분한다.

중앙 화면과 계기판을 모두 목표로 한다는 선택도 받았다. 실제 계기판 출력 API와 권한은 아직 확인하지 않았으므로 PC 계기판 미리보기와 실제 출력 지원을 구분한다. 첫 버전의 구체적인 모델·장면·기능 범위는 `docs/superpowers/specs/2026-10-28-low-friction-driving-design.md`에 설계안으로 작성했으며 사용자 확인 전이다. 이번 기록은 구현 완료나 세부 설계 승인 기록이 아니다.

## 2026-10-28 Phase 0 SDK 입력 진단 화면

목적은 조향·브레이크 데이터 전달 경로를 실제로 관측하는 것이다. 사용자가 만든 Kotlin·Compose 앱을 유지하고 공식 Vehicle SDK 2.3.2의 공개 typed API를 사용했다. 별도 게임 엔진이나 물리 모델을 도입하지 않았다.

선택 근거는 공식 [SDK 설정](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/Vehicle/project-setup), [권한](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/Vehicle/vehicle-permission), [capability](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/Vehicle/check-capability) 문서와 로컬에 내려받은 동일 버전 sources.jar의 실제 시그니처다.

일정 간격으로 get을 반복하는 대신 register 콜백을 사용한다. 초기 현재값은 get으로 확인한다. 뒤늦게 도착한 초기 조회 결과가 더 새로운 변경 알림을 덮어쓰지 않게 했다. 화면·SDK 코드를 두 파일로 나눠 역할을 설명할 수 있도록 했다.

AAOS 프로퍼티 직접 사용이나 reflection 기반 탐색은 이번 실험에 필요하지 않다. 공식 공개 API로 필요한 두 입력을 확인할 수 있고 이후 권한·호환성 근거를 추적하기 쉽기 때문이다. 가속·기어·차량 제어 기능은 추가하지 않았다.

null과 오류는 실제 상태와 구분하고, 조향값에는 임의 부호·조향비 보정을 적용하지 않는다. capability가 읽기를 허용할 때만 조회·구독한다. Manifest에는 CAR_DRIVE만 추가된 상태를 유지했다.

검증은 debug APK 빌드, 설치·실행, 양방향 조향 및 브레이크 false/true/false 수신으로 수행했다. 이 코드는 진단용 실험이며 아직 완성된 차량 입력 계층으로 간주하지 않는다. 서비스 무응답 timeout, 입력 timestamp·staleness, 주행 제한, lifecycle 회복 시험이 남아 있다.

## 2026-10-28 주차 및 UX 제한 진단

기어 P와 CarUxRestrictions를 모두 읽어 판정한다. UX만 보거나 속도 0만으로 허용하는 방식 대신, 사용자의 주차 중 사용 원칙에 따라 P 확인·DO=false·flags=0을 동시에 요구한다. 문서에 없는 미래 플래그도 무시하지 않고 제한으로 취급한다.

기어는 SDK의 숨겨진 Gear가 아닌 AAOS 공개 GEAR_SELECTION으로 조회한다. android.car는 플랫폼 공유 라이브러리이므로 SDK 의존성을 APK에 번들하지 않는다. 선택적 library 선언과 API29+ 비차단 연결 방식을 사용한다. minSdk28은 유지하며 그 환경에서 이 리더는 미확인/실행불가로 남는다. API28에서도 이 기능을 제공하려면 별도 구현과 검증이 필요하다.

초기 gear read는 worker에서 실행하고, 더 새로운 callback이 있으면 이전 read 결과를 폐기한다. 화면 재진입과 서비스 연결 세대는 active/epoch로 구분한다. 게임은 아직 없으며 현재 결과는 사전조건 표시다. 플랫폼 제한을 우회하거나 DO 앱으로 위장하지 않는다.

## 2026-10-28 Unreal 첫 프로젝트

사용자는 C++에 익숙하고 Unreal에서 작업을 시작하기로 했다. 기존 `android` 진단 앱을 보존하고 별도 `unreal/BeyondPhysics` 프로젝트를 만든다. 작은 첫 시제품은 평면 도로·임시 차량·카메라로 한정한다. 추가 예외 시험을 선행 조건으로 두지 않되 물리 모델 도입 시 해당 모델의 근거·오차 검증은 유지한다.

Unreal5.8.4, 가벼운 렌더링 설정, Windows D3D11로 장면 편집·PC 실행 기반을 만든다. 차량은 기본 Cube/Cylinder를 조립하고 물리 시뮬레이션을 끈다. 엔진 기본 차량 모델을 검증된 자체 동역학이라고 부르지 않는다. 모델·재질은 엔진 기본 자산과 직접 생성한 단색 재질만 사용했다.

C++ 모듈을 추가하기 전에 콘텐츠 장면을 생성해 도구 업데이트와 독립적으로 시각적 결과를 확보했다. `.Target.cs`/`.Build.cs`는 Unreal의 빌드 설정이고, 프로젝트 동작은 앞으로 C++로 작성한다. 장면 생성 Python은 편집 도구이며 배포 게임의 실시간 물리 계층이 아니다.

첫 빌드에서 NetFxSDK가 없어 실패한 뒤 공식 Visual Studio 구성 요소 .NET Framework4.8 SDK/TargetingPack을 추가해 재빌드에 성공했다. 상세 버전과 로그는 프로젝트 현황·실험 기록에 남긴다. Python Rotator 인자 순서(roll,pitch,yaw)가 C++ FRotator와 달라 바퀴가 눕는 문제는 키워드 인자를 사용해 수정했다. 이후 회전 인자와 단위를 언어 경계에서 명시한다.

## 조향 방향 검증·정지 출발 AWD·1인칭
